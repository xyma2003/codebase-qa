# Codebase Q&A 产品方案

版本：0.1。日期：2026-11-10。状态：用户已同意，按阶段实施。

## 产品定位

帮助开发者接手陌生 GitHub 仓库，理解实现、追踪问题，并获得有源码依据的修改方案。关键结论能够回到具体代码版本、文件和行号。

核心用户是需要了解开源项目、接手现有代码或准备修改功能的开发者。首版以公开 GitHub 仓库和 Python 项目为主要验收范围；其他语言先提供文本检索。

## 核心任务

1. 了解项目：用途、目录职责、入口和主要模块。
2. 追踪实现：定位功能经过的文件、函数和配置。
3. 准备修改：说明涉及文件、修改理由、实施顺序和验证方法。

典型问题：我想让这个项目支持真正的多轮对话，需要修改哪些地方？

结果应包含当前实现、问题依据、修改位置和验证建议。证据不足的部分明确说明；静态分析不能证明的运行行为保留为待验证项。

## 第一版用户流程

输入仓库地址 → 导入代码快照 → 查看项目概览 → 围绕问题研究 → 核对源码 → 连续追问 → 获得修改方案。

| 功能 | 交付行为 |
| --- | --- |
| 仓库导入 | 导入指定分支，记录实际 Commit SHA |
| 项目概览 | 解释用途、目录、入口和主要模块，并给出依据 |
| 实现分析 | 根据问题跨文件查找，解释关键执行流程 |
| 修改规划 | 列出涉及文件、理由、顺序和验证建议 |
| 连续追问 | 保持正确的仓库、代码版本和对话上下文 |
| 源码核对 | 点击引用，查看对应版本的代码和上下文 |

首版交付分析报告和修改方案。生成补丁、执行目标仓库的测试，进入后续阶段。

## 界面原则

保留清晰的仓库工作区：仓库与版本、分析与对话、按需展开的源码。过程区展示实际搜索、读取和任务状态。使用简短、常见的文案，保持简洁；不随意增加背景色、宣传语或无关提醒。

## 质量标准

- 检索能找到问题所需的关键代码，而不仅是相似文字。
- 关键事实有可核对的证据，引用位置与结论支持程度分别评估。
- 修改方案覆盖必要文件，验证建议可以实际执行。
- 仓库没有答案时，不虚构实现。
- 记录任务成功情况、耗时、调用次数和可获得的用量信息。

固定评测覆盖项目理解、功能定位、修改影响和无答案问题。评测样本与模型配置在比较时保持一致；正确率目标在测得基线后确定。

## 实施阶段

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| 0 | 复现当前版本，保存环境、配置和结果 | 真实完成仓库导入、索引及模型问答，留下成功记录 |
| 1 | 版本快照、按行读取、引用校验和仓库隔离 | 新旧版本均可定位，引用不混用 |
| 2 | 概览、跨文件分析、修改规划和连续追问 | 完成了解项目到获得修改方案的完整流程 |
| 3 | 固定评测，对比检索、上下文和历史答案策略 | 能说明提升、退化、成本与适用范围 |
| 4 | 限定任务的补丁生成与隔离测试 | 交付代码变更和真实验证结果 |

## 迭代规则

每次做一个可验收的小改动。阶段完成后更新已验收、下一步和待验证想法。新增想法记录问题、证据、成本及所属阶段；改变定位或明显扩大范围时先与用户确认。

候选扩展：Issue 辅助定位、Commit 或 PR 影响分析、补丁生成与测试。候选方向不自动进入当前范围。
